# योजना सारथी (Yojana Saarthi) — Government Scheme Eligibility Checker

Ask a few questions about yourself, get back the list of **76 Indian
government schemes** you are actually eligible for — plus the ones you *almost*
qualify for, with the exact criteria you missed.

Real full-stack app: **React (Vite) frontend + Node/Express API + PostgreSQL**,
deployed as a single process from one repo.

The frontend is **not** committed as a build. `frontend/dist` is generated by

you. If you start the server without building, the API still works but no page is
served, and the server says so in the log.

## Run it locally

**1. Prerequisites** — [Node.js](https://nodejs.org) 22+ and a PostgreSQL
database. The free tier at [neon.tech](https://neon.tech) is enough.

**2. Install**

```bash
git clone <your-repo-url>
cd yojana-sarthi-fullstack
npm install
```

The root `npm install` also installs `backend/` and `frontend/` for you.

**3. Configure**

```bash
cp backend/.env.example backend/.env
```

Then fill in `backend/.env`:

| Variable         | Required | Notes                                                        |
| ---------------- | -------- | ------------------------------------------------------------ |
| `DATABASE_URL`   | yes      | Neon/Render connection string                                 |
| `JWT_SECRET`     | yes      | 32+ random chars — `node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"` |
| `PORT`           | no       | Defaults to `3000`                                            |
| `APP_URL`        | no       | Public URL used in reset/verify emails and as the default CORS origin. Defaults to `http://localhost:3000`; **set it on Render** |
| `CORS_ORIGINS`   | no       | Extra comma-separated browser origins allowed to call the API |
| `ADMIN_EMAILS`   | no       | Comma-separated; these accounts get the admin dashboard       |
| `RESEND_API_KEY` | no       | Without it, reset/verify emails are logged to the console      |
| `MAIL_FROM`      | no       | Verified Resend sender, e.g. `Yojana Saarthi <no-reply@yourdomain>` |

**4. Build the frontend**

```bash
npm run build
```

**5. Start**

```bash
npm start          # API + UI on http://localhost:3000
```

The server creates its tables and upserts all 76 schemes on boot, so
`npm run seed` is only needed to seed a database by hand.

**6. Frontend hot reload (optional)**

```bash
npm run dev        # terminal 1 — API on :3000
npm run dev:client # terminal 2 — Vite on :5173, proxies /api to :3000
```

**Or skip Node entirely and use Docker**

If `backend/.env` is already filled in, Compose builds the image and starts the
app against the same database — no local `npm install`, no `npm run build`:

```bash
docker compose up -d --build   # http://localhost:3000
docker compose logs -f app
docker compose down
```

Compose reads `backend/.env` directly, so there is nothing to configure twice.
The image never contains it: `.dockerignore` excludes `**/.env` from the build
context, and Compose only injects the file at runtime.

Note that this writes to the same database you use with `npm start`, so scheme
check history and test accounts land in your real dev database.

## How eligibility matching works

Every scheme carries a `criteria` JSON column. `backend/lib/eligibility.js`
evaluates a user's answers against it — nothing is hardcoded per scheme, so
adding or editing one is a data change:

```json
{ "minAge": 18, "maxAge": 120, "occupations": ["farmer"], "maxIncome": 100000 }
```

The engine returns:

- **matches** — every criterion satisfied
- **near-matches** — schemes missed by one or two criteria, each labelled with
  *what* was missing, so the UI can show how close someone was

**Adding a scheme:** append an object to the `schemes` array in
`backend/seed.js` and restart (or `npm run seed`). Upserts are keyed on `id`, so
user accounts and check history are untouched.

## API

All routes are prefixed `/api`. Authenticated routes take
`Authorization: Bearer <token>`.

| Method   | Route                        | Auth   | Purpose                            |
| -------- | ---------------------------- | ------ | ---------------------------------- |
| `GET`    | `/health`                    | –      | Liveness probe (process is up)     |
| `GET`    | `/ready`                     | –      | Readiness probe (database answers) |
| `POST`   | `/api/auth/register`         | –      | Create an account, returns a JWT   |
| `POST`   | `/api/auth/login`            | –      | Returns a JWT                      |
| `POST`   | `/api/auth/forgot`           | –      | Emails a reset link                |
| `POST`   | `/api/auth/reset`            | –      | Consumes a reset token             |
| `POST`   | `/api/auth/verify`           | –      | Consumes an email verification link |
| `POST`   | `/api/auth/resend-verification` | required | Sends a fresh verification email |
| `GET`    | `/api/schemes`               | –      | All schemes                        |
| `POST`   | `/api/check`                 | optional | Matches + near-matches            |
| `GET`    | `/api/check/history`         | required | The caller's past checks          |
| `GET`    | `/api/applications`          | required | Tracked applications              |
| `POST`   | `/api/applications`          | required | Start tracking a scheme           |
| `PATCH`  | `/api/applications/:schemeId`| required | Update tracking status            |
| `DELETE` | `/api/applications/:schemeId`| required | Stop tracking                     |
| `GET`    | `/api/admin/stats`           | admin   | Analytics dashboard               |

Unmatched `/api/*` paths return `404 {"error":"Not found"}` rather than the HTML
shell, so a client never gets HTML where it asked for JSON.

## Deploy

### Render (free, recommended)

Push to GitHub, then on Render pick **New → Blueprint** and connect the repo.
`render.yaml` fills in the rest:

- Build: `npm ci --prefix frontend --include=dev && npm ci --prefix backend --include=dev && npm run build`
- Start: `npm start`
- You supply `DATABASE_URL`; `JWT_SECRET` is generated for you
- `APP_URL` is pre-set to the service URL so reset/verify emails link to the
  right place. Set `RESEND_API_KEY` (and ideally a verified `MAIL_FROM`) to
  actually deliver email, and `ADMIN_EMAILS` if you want the admin dashboard.

Render's free tier sleeps after ~15 minutes idle and takes ~30s to wake. Upgrade
to remove that.

### Docker

Build from the **repo root** (the context needs both packages):

```bash
docker build -t yojana-sarthi .
docker run -p 3000:3000 --env-file backend/.env yojana-sarthi
```

Stage 1 installs both packages and builds the frontend; the runtime image keeps
only production dependencies plus the built `dist`, and `.dockerignore` keeps
`.env` and `node_modules` out of the build context.

The same image works on Railway, Fly.io or any Docker host.

## Tests and CI

```bash
npm test            # backend + frontend test suites
npm run lint
npm run format:check
```

`.github/workflows/ci.yml` runs four jobs on every push and pull request to
`main`: **lint & format**, **backend tests**, **frontend tests & build**, and
**docker build & smoke test**.

The first three need no configuration — tests stub the database, so no
`DATABASE_URL` is required. The docker job is the one that would otherwise rot
silently: it builds the real image, then starts it against a throwaway Postgres
service and asserts the container actually works — `/ready` confirms the
container can reach its database, `/api/schemes` returns all 76 schemes, the
built UI is served, and an unknown `/api` path still 404s as JSON. A broken
`Dockerfile`, a bad `.dockerignore` entry, or a frontend build that only fails
inside a container all fail CI here instead of at deploy time.

## Health checks

`/health` and `/ready` answer different questions on purpose:

- **`/health`** — is the process alive? It never touches the database, so it
  stays green even when `DATABASE_URL` is wrong. Use it as a liveness probe.
- **`/ready`** — can the app actually serve? It runs `SELECT 1` and returns
  `503` until the database answers. Use it as a readiness probe.

This split exists because startup **swallows seed errors** (one malformed scheme
should not take the whole API offline), which means a misconfigured
`DATABASE_URL` still starts a server that answers `/health` with `200` while
every real route fails. The image `HEALTHCHECK` and the Render blueprint's
`healthCheckPath` both point at `/ready` for exactly that reason — do not point
them at `/health` or the misconfiguration stays invisible.

## Rotating the database password

The app only ever reads the connection string from `process.env.DATABASE_URL`, so
rotating the Neon password means updating exactly two places and nothing else —
there is no credential baked into the image, and the frontend talks to `/api`
over relative paths, so it has no idea a database exists.

| Where                          | How it gets the value                     |
| ------------------------------ | ----------------------------------------- |
| Local dev / Docker             | `backend/.env` (read at runtime by Compose) |
| Render                         | Dashboard env var — `render.yaml` uses `sync: false` |

CI is unaffected: `.github/workflows/ci.yml` starts its own throwaway Postgres
service with its own password.

**1. Reset the role password in Neon**

Open the project's **Dashboard** and click **Connect**. Inside the modal, open
the **role** menu and choose **Reset password**, then **Reset**. The new password
is shown once — copy it, then copy the connection string from the same modal.

Doing it from the Connect modal is the shortest path because the reset and the
copy happen in one place, and the string you copy is guaranteed to match the
password. To do them separately, the sidebar path is **BRANCH** selector →
**Postgres database** → **Roles** → the role's **⋯** menu → **Reset password**.
Neon moved *Roles* and *Databases* under one collapsible **Postgres database**
item in August 2026, so older guides that say "the *Roles & Databases* tab" no
longer describe the Console.

**Copy the whole string, do not retype it.** Only the password segment changes —
the host and database name stay the same — but retyping a generated password can
drop a character that the URL had encoded. You can keep `?sslmode=require` at the
end: `db.js` chooses TLS itself (off for `sslmode=disable` or a `localhost` host,
on otherwise) and strips the parameter before connecting, so it is harmless.

The reset is branch-scoped to whichever branch the **BRANCH** picker is showing.
Child branches keep the old password until you reset the role on each of them.

**2. Push the new value to Render**

Render → your service → **Environment** → `DATABASE_URL` → paste → **Save**.
Saving restarts the service by itself; you do not need to redeploy.

**3. Update `backend/.env`** with the same string, and restart whatever you run
locally. The `pg.Pool` is built when `db.js` is first required, so a running
`npm start` process keeps its old connections and never notices the change.
`docker compose up -d` (no rebuild needed) re-reads the file for the container.

**4. Verify with `/ready`, not `/health`**

```bash
curl -i http://localhost:3000/ready
curl -i https://<your-app>.onrender.com/ready     # 200 {"status":"ready"}
```

`/ready` runs `SELECT 1`, so it is the only endpoint that proves the new
password actually works. `/health` returns `200` on a server that cannot log
into the database at all, so checking it here tells you nothing. If `/ready`
gives you `503`, the password in the connection string is the wrong one or has a
character the URL encoding dropped — compare it against the string from the
Connect modal rather than retyping it.

**Expect a short outage between steps 1 and 2.** The reset takes effect
immediately, so every new connection using the old password fails while Render
is still restarting (its free tier also sleeps after ~15 min idle and takes ~30s
to wake). Already-open connections survive, so the window is one deploy cycle,
not data loss. If the Console is slow to hand over the new string, paste it into
Render the moment you have it — step 3 is the only step you can do while the app
is already down. For a real service with live traffic, create a second role in
Neon, roll the new string out everywhere, then reset the old role's password to
actually invalidate the leaked credential.

Recovering from a mistake is just repeating the runbook: reset the password
again in Neon, copy the new string, update both places. Nothing in the database
is touched by a rotation.

## Accuracy note

Scheme amounts, income limits and eligibility rules are indicative and reflect
general knowledge of these schemes — **government rules change over time**. The
UI tells users to verify on the official portal before applying, and they should.
